# Audio, feedback and text injection internals

Recording, cues, muting other apps and getting the text into the focused app. Rules: `src/nexusvox/CLAUDE.md`. Module paths such as `app/core.py` are relative to `src/nexusvox/`; paths that start with a top-level folder (`tests/`, `docs/`, `docker/`, `scripts/`) are from the repository root.

## SendInput INPUT Struct

The ctypes `INPUT` struct union **must** include `MOUSEINPUT` (not just `KEYBDINPUT`) so that `ctypes.sizeof(INPUT)` returns 40 bytes on 64-bit Windows. With only `KEYBDINPUT` the struct is 32 bytes, and `SendInput` silently returns 0 — no error code, no exception. The modifier-release step (`_release_all_modifiers`) and configurable `injection_delay_ms` are also required because the push-to-talk hotkey (Ctrl+Win) can leave stale modifier state. `inject_text` first polls `GetAsyncKeyState` until the user has physically released all modifiers, because the hotkey deactivates on the *first* modifier going up. **Never wrap the Ctrl+V `SendInput` in `AttachThreadInput`**: SendInput does not need it, and detaching right after the call re-syncs the target thread's key state while it may still be processing the V keydown — the app then reads Ctrl as up and types a literal "v" (intermittent). `_paste_via_message` uses `GetGUIThreadInfo` to find the focused control for the same reason. **Clipboard writes go through `clipboard.set_text`, never `pyperclip.copy`**: it adds the formats `CanIncludeInClipboardHistory` / `CanUploadToCloudClipboard` (DWORD 0) and `ExcludeClipboardContentFromMonitorProcessing`, so the pasted text and the restored clipboard stay out of the Win+V history. Reads still use `pyperclip.paste`. The one entry NexusVox cannot keep out is the app's own Ctrl+C in polish's clipboard fallback. `set_text` retries `OpenClipboard` for ~500 ms (`_OPEN_ATTEMPTS`, as long as pyperclip waited) and raises `ClipboardError`; `inject_text` puts the user's clipboard back ~300 ms after Ctrl+V (`_RESTORE_DELAY_S`), because Electron apps and terminals read the clipboard late and pasted the old content when it came back after 100 ms. It returns the `time.monotonic()` at which the text was in place (before that wait), and `latency_ms` ends there, so the restore delay never counts as latency. Every caller of `inject_text` catches `ClipboardError`: a dictation then plays the error beep, is still saved and kept as `_last_typed` (the paste key pastes it).

## Dictation Microphone

`[audio].device` names the input device dictation records from (Settings > Dictation, the first-run setup's Microphone step; empty is the system default input). `AudioCapture.start` reads it at every recording and resolves it with `audio/devices.py` `find_input_device`, the lookup the meeting microphone shares: the named device on WASAPI (its names are the full ones; MME cuts them at 31 characters), the default input when the name is gone. A WASAPI device opens at our 16 kHz through `WasapiSettings(auto_convert=True)`, since shared mode otherwise only opens at the device's own rate. The setup's level meter (`audio/meter.py` `LevelMeter`, `GET /api/setup/mic-level`) opens its own input stream on the same device at the device's rate, keeps the loudest chunk since the last poll and closes the stream by itself 3 s after the last poll; it counts in `audio/state.py`, so the device list is not refreshed under it.

## Dictation Feedback

`dictation/overlay.py` + `FeedbackCues._cue` in `app/feedback.py` - `[feedback].mode` (`sound` when the key is missing, so existing installs keep their chimes; the template a fresh install is created from says `visual`; `visual`, `both`; dashboard Settings > Dictation, `POST /api/settings/feedback-mode`) is read on every cue, so a change is live. `App._cue(beep, state)` is the one place a dictation signals a state: the chime through `_play` unless the mode is `visual`, the overlay through `Overlay.show` unless it is `sound` (`RECORDING` on the start, `PROCESSING` on the stop, `ERROR` for every error beep, `CONFIRMED` - a brief green bar - for the flag confirmation, so Visual-only still confirms it). The cycle's `finally` shows `"done"` (hides) unless the hotkey is held again (then it shows `RECORDING` at once: the next take is spoken before its server connection is up) and for a phone recording never; `ERROR` and `CONFIRMED` are timed states that `done`/`processing` never cut short. Phone recordings keep their plain sounds; meeting start/stop beeps never touch the overlay. `OverlayModel` is the pure, thread-safe state (hidden/recording/processing/error, a 28-bar level history; an error lasts `ERROR_S` and `done` never cuts it short); `AudioCapture.on_rms` feeds it from the audio thread (`level_from_rms`: -60..-20 dB). `Overlay` runs one Tk toplevel on its own thread (created hidden at start when the mode is not `sound`, else on the first cue; Tkinter is stdlib, no new dependency; `Overlay.failed` - set when the window cannot start or its tick raises, which also hides it - makes `_cue` play the chime whatever the mode; the dashboard switch calls `App.on_feedback_mode`, which builds the window then, not mid-dictation; the window uses its own `WinDLL("user32")` so its prototypes never change what `injector` and `window_manager` get back; a new recording is placed again, so it follows the focus to another monitor; `AudioCapture.rms_wanted` keeps the overlay feed off the audio thread in `sound` mode; the chunk statistics are computed for every chunk with a dot product, no temporary array, for the recording summary): `overrideredirect`, topmost, `-transparentcolor` for the rounded pill, and the extended styles `WS_EX_NOACTIVATE | WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_LAYERED` re-applied right before every show (Tk rewrites them when it maps the window), shown with `SetWindowPos(SWP_NOACTIVATE | SWP_SHOWWINDOW)`, placed at the bottom centre of the work area of the monitor holding the foreground window (primary monitor when none). **Focus:** merely creating a Tk root steals the foreground for ~10 ms, even withdrawn, so `_loop` hands it straight back (`SetForegroundWindow(previous)`); showing never activates. The polish key path shows it as well (its error and processing states go through the same cues); an error that has a visual form but no chime (a failed cycle) is `_cue(None, ERROR)`.

## Mic Guard

`audio/mic_guard.py` — opt-in via `[mic_guard].enabled` (dashboard Settings > Dictation toggle; the guard is always constructed and `app/events.py` checks the flag on every hold, so the toggle is live). On key-down every WASAPI audio session on the default *capture* endpoint (pycaw's `AudioUtilities` helpers only look at the render endpoint, so `enumerate_capture_sessions` asks `IMMDeviceEnumerator` for `eCapture` explicitly) that is not PID 0 and not our own PID is muted through `ISimpleAudioVolume`, but only if it was unmuted; on key-up those sessions are set back to unmuted. Never the endpoint device. NexusVox is a single process, so `os.getpid()` is the whole exclusion. `MicGuard` is pure logic over a `CaptureSession` protocol (tests use fakes); `WasapiCaptureSession` is the real thing. Sessions are re-enumerated on every hold and release and matched by `GetSessionInstanceIdentifier`, so no COM pointer ever crosses threads and COM is initialised per thread (`ensure_com`, MTA, `RPC_E_CHANGED_MODE` tolerated). `SetMute` costs ~40 ms per session and pynput runs the hotkey callbacks inside the low-level keyboard hook, so `app/events.py` calls `hold_async()` / `release_async()`: one worker thread, FIFO, so a very short tap still muted-then-restores in order; the record-start event is set at the same time, dictation start is not delayed. Nothing may stay muted: `release()` is idempotent and runs on key-up, in the `finally` of `_transcription_cycle`, in `_shutdown`, via `atexit`, and from a watchdog (`watchdog_s`, default 30 s) that only fires when `HotkeyListener.modifiers_physically_down()` (GetAsyncKeyState, independent of the hook) says the keys are up — a long dictation re-arms it. During a hold the muted sessions are in `mic_guard_state.json` next to the database; `restore_leftovers()` runs at startup and matches on the stable `GetSessionIdentifier` too, because Windows persists per-app mute across app restarts. Known gaps: an app that starts capturing mid-hold is not muted until the next hold, and **Discord ignores session mute entirely** (the mute flag is set, yet Discord's voice activity ring still lights; an ordinary WASAPI/MME capture stream and a Chrome getUserMedia stream both go to exactly 0.0 within 300 ms, so browser calls are covered). The supported answer for Discord is its own *Push to Mute* keybind on the NexusVox hotkey; say so in any user-facing text about this feature.

## Streaming Errors

`App._stream_audio` reads the whole recording up to its end marker even when sending to the transcriber fails (the audio is kept), then raises; `_transcription_cycle`'s error path calls `_abort_recording` (stops a microphone that still records, cancels a stream task that still reads); the transcriber is disconnected once (`hang_up`): right after `finish()` (and before a paste-last or a polish tap), so an LLM or a paste never holds an idle server session, with the cycle's `finally` as the backstop, after the mic guard. Stopping at the failure would leave the unread chunks and the end marker in `AudioCapture`'s persistent queue, and every later dictation would be the previous one. `AudioCapture.start()` also starts with a fresh queue. **Log:** each chunk's RMS and frame count go into `RecordingLevels`; the per-second `Audio: chunks=... rms=...` line is DEBUG only. `AudioCapture.stop()` closes the stream (`_close_stream`: the stream counts as closed even when PortAudio raises) and writes one INFO line per recording in a `finally`, so a device that fails still leaves it: `Audio: 19.0 s, 189 chunks, rms avg -48 dB, peak -32 dB, 12% silent`. The length adds up the frames the callbacks delivered, and a chunk under `SILENT_DB` (-60 dB) counts as silent. A recording with at least `SILENT_WARNING_SHARE` (95%, a muted microphone often clicks once when the stream opens) silent chunks that lasted at least `MIN_SILENCE_WARNING_S` (0.5 s, so a tap is not blamed on the microphone) adds one WARNING naming the device. `start()` first closes a stream an earlier failed stop left open, so it cannot feed the new recording's statistics. A phone recording has no summary: `_stream_audio` keeps its `Streamed N audio chunks` line at INFO (DEBUG for the microphone). Only levels are logged, never audio or text. `tests/test_audio_summary.py`. The auto engine's CPU preload runs on a throw-away `LocalParakeetTranscriber`: connecting or disconnecting the instance a running take uses wiped its buffer mid-recording. A recording that ends with no audio frames (a WAV of only its header) is never sent: `_transcription_cycle` logs `Recording has no audio frames, nothing to transcribe` before `finish()` and ends quietly for every model (a polish tap still polishes with the default instruction).

## Audio Persistence

Each recording saved as 16kHz mono WAV in the configurable `audio/` directory alongside the database, unless `[database].store_audio` is false (`App._store_audio` checks the flag per recording, so the dashboard toggle is live; the transcript row is saved either way with `audio_path` NULL, which the Review queue already filters out). Enables batch review with playback in the dashboard Review/Edit tabs.
