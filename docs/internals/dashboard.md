# Dashboard internals

The Flask server, its modules, the look and every tab. Rules: `src/nexusvox/dashboard/CLAUDE.md`. Endpoint list: `docs/internals/dashboard-api.md`. Module paths such as `app/core.py` are relative to `src/nexusvox/`; paths that start with a top-level folder (`tests/`, `docs/`, `docker/`, `scripts/`) are from the repository root.

## Server

Flask server starts once on first tray click (left-click on the icon or the Dashboard menu item), runs in a daemon thread on `127.0.0.1:47392`; when another program holds that port, `_bind_server` binds the first free one of `_FALLBACK_PORTS` (47400-47409; 47393 is the remote mic) on a socket of its own (exclusive on Windows, `SO_EXCLUSIVEADDRUSE`; werkzeug exits the process when its own bind fails, so it gets the socket as `fd`) and `open_dashboard` opens that (`_port`), and with every port held it logs an error and shows a message box (`single_instance.show_message`) instead of opening a dead tab; that failure is remembered (`_start_failed`), so later calls neither re-probe nor build a second `DashboardAPI`. Static files in `src/nexusvox/dashboard/static/` (HTML, CSS, JS, bundled Chart.js — no CDN). API endpoints under `/api/*` return JSON, consumed by vanilla JS `fetch()` calls.

The page's JavaScript is one file per tab plus shared helpers, flat in `static/` (`pyproject.toml` packages `dashboard/static/*`), loaded by `index.html` in this fixed order: `dashboard-core.js` (fetch guard, `setStatus`, theme, `api`, feature flag state, tab switching, `NexusVoxExt`, shared helpers), `dashboard-settings.js`, `dashboard-feedback.js` (the Feedback tab's form), `dashboard-settings-models.js`, `dashboard-settings-vocabulary.js`, `dashboard-analytics.js`, `dashboard-edit.js`, `dashboard-review.js`, `dashboard-upload.js` (the upload dialog, file jobs, exports and upload actions), `dashboard-meetings.js` (meeting recording, live transcript, meeting settings), `dashboard-recordings.js` (the Recordings tab: list, detail pane, extension tabs), `dashboard-home.js` (the Home tab), `dashboard-dev.js`, `dashboard-init.js` (feature flag loading, the tab and `hashchange` wiring and the `DOMContentLoaded` loaders, last, so no tab goes live before the files its handlers call have run). They are classic scripts sharing one global scope, not modules, so extension panels and inline handlers reach the same names as before. A function is hoisted only within its own file: top-level code may use only what its own or an earlier file defines, while anything inside a handler or a function called after load can use every file. `escapeHtml` escapes quotes too, so its result is safe in a quoted attribute. `test_dashboard_scripts.py` pins the order and runs the files together under Node against a stand-in page built from the ids in `index.html`. Tests read them through `tests/dashboard_js.py`, joined in load order; `scripts.py` (`page_scripts`) is the one reader of the script tags, shared with both packaging checks.

- `guard.py` — access control, one `before_request` hook installed first in `_create_app`, so every route (extension blueprints included) is covered: the Host header must be `127.0.0.1`/`localhost` with the dashboard port (DNS rebinding), an `Origin` header must be one of those origins, `Sec-Fetch-Site` must be `same-origin` or `none`, and every request needs the `HttpOnly`, `SameSite=Strict` session cookie (random per run) or gets 403 (JSON with an `X-NexusVox-Denied` header for `/api/*`, which a `fetch` wrapper at the top of `dashboard-core.js` turns into a reopen-from-tray banner). The cookie comes from `GET /?launch=<secret>`: `open_dashboard` builds that URL with a single-use secret (60 s TTL) held in memory; the server is bound before `_server_started` is set, and a busy port opens no browser, so a program that only requests `/` gets nothing. After a restart an old tab is refused until it is reopened from the tray. Tests: `test_dashboard_guard.py`; `tests/conftest.py` makes every `app.test_client()` signed in.
- `analytics.py` — the one import path for the SQLAlchemy query functions, which live in `analytics_*.py`, one module per topic: `analytics_overview` (overview cards, polish and command rows, uploads), `analytics_usage` (charts over time, languages, words, models, apps), `analytics_accuracy` (corrections, learn outcomes, dictionary use), `analytics_week` (the weekly report), `analytics_review` (the flagged and review lists) and `analytics_common` (`_apply_date_filter`). A new public query goes into its topic module and is re-exported here; `tests/test_analytics_exports.py` pins the names. Private helpers stay in their module
- `api.py` — `DashboardAPI`: joins the topic mixins below and owns the state they share (`__init__`). The Flask routes that call it are in `routes_*.py`
- `api_base.py` — the shared `logger` (every topic module imports it, so all log as `nexusvox.dashboard.api`) and `DashboardState`, the base of every mixin: it declares the state and the methods of other mixins a mixin may use, and holds `_db_dir`. A mixin that uses something new of another one declares it there; `tests/test_dashboard_api_contract.py` fails otherwise, and on a declared name that is gone or unused, since no type checker runs here. `MeetingsMixin` and `MeetingTranscriptMixin` use each other: they are two halves of one topic
- `api_*.py` — the mixins, one per topic: `api_models` (models, device), `api_settings` (settings page, language model), `api_commands` (voice and OS commands), `api_analytics` (statistics, benchmarks), `api_review` (flagged, review), `api_vocabulary` (dictionary, polish presets), `api_files` (uploads and the rows uploads and meetings share), `api_meetings` (recording, pending meetings, meeting settings), `api_meeting_transcript` (the transcription job). A test patches a name in the module that uses it. A name several modules import has a copy in each, and a patch on one does not reach the others: `save_config` (use the `no_config_save` fixture), `cuda_available` and `convert_to_wav` (use `patch_api(name, value)`, which replaces every copy)
- `routes_*.py` — the Flask routes, one module per topic, matching the mixins: `routes_models`, `routes_settings`, `routes_meetings` (also `/api/settings/meeting-*`), `routes_commands`, `routes_analytics` (also the benchmarks), `routes_review`, `routes_vocabulary`, `routes_files` and `routes_extensions`; `routes_base` holds `_switch`. Each has a `register(app, api)`, and `_create_app` calls them through `_ROUTE_MODULES`; `tests/test_dashboard_routes.py` fails when a module is left out. Modules with flag-gated routes read `api.experimental` there, at start. Routes go straight on the app with `@app.route`: a blueprint would rename every endpoint. `routes_extensions` logs as `nexusvox.dashboard`, the name its lines always had (`tests/test_extensions.py` pins it). `__init__.py` keeps `_create_app`, `/`, `/api/features` and the server code, because tests patch `_make_server`, `_PORT` and `show_message` there
- `benchmarks.py` — benchmark JSON file I/O and cross-model comparison (Dev tab, experimental)
- `file_jobs.py` — in-memory registry of file transcription jobs (upload progress in the Recordings tab)

## Look

**Status colour rule (every status line, hint and badge).** Green (`.status-line.ok`) = works as expected ("Model server reachable"). Yellow (`.status-line.warn`, `.badge.warn`, token `--yellow`) = works, but with a caveat the user should know: slower on the CPU (the Cleanup latency hint), Experimental/Beta, Alt in the dictation or meeting hotkey (`renderAltHint`, `#hotkey-alt-hint` / `#meeting-hotkey-alt-hint`, shown and cleared live), a fallback is active (speech engine "Auto" resolved to the CPU; a GPU asked for explicitly without CUDA is red). Red (`.status-line.down`) = does not work or is not reachable ("No translator"). No class = neutral (checking, idle). JS sets the state only through `setStatus(el, state, text)` (state `"ok"`, `"warn"`, `"down"`, anything else is neutral; it touches only the state classes, so other classes on the element stay; an HTML template leaves the state class out and calls `setStatus` when it shows the line); static hints that are always a caveat carry `status-line warn` in the HTML. Do not add a new colour or write `status-line` class names by hand. The dashboard has one (dark) theme, so the tokens in `style.css` are the single place to adjust contrast; `tests/test_status_colours.py` covers the rule.

Aurora Precision theme, shared with the website. Tokens are the `:root` variables in `style.css` (`--bg`, `--surface*`, `--border*`, `--text*`, `--accent`/`--accent-light`, `--green`, `--yellow`, `--red` (status colours, see below), `--orange` (only the Dev tab's identity, never a status), `--scrollbar-thumb`/`--scrollbar-thumb-hover`, 18px cards); `COLORS` at the top of `dashboard-core.js` reads them (and the font) from the computed style at startup for Chart.js, so `style.css` is the only place to change a color; chart-only tints are the `--accent-soft`, `--accent-fill` and `--green-fill` tokens. Geist and Geist Mono (SIL OFL) are bundled flat in `static/` (`Geist-Variable.woff2`, `GeistMono-Variable.woff2`, license in `Geist-OFL.txt`; `pyproject.toml` packages `dashboard/static/*`, so they must stay flat) - no CDN, the dashboard works offline. Scrollbars are thin and dark on every tab, with a transparent track (`recordings.css`: `::-webkit-scrollbar` rules for Chromium, which ignores them once `scrollbar-color` is set, so `scrollbar-width` / `scrollbar-color` apply only where `::-webkit-scrollbar` is unsupported, as in Firefox). The `<header>` is a left sidebar (brand + stacked `.tab` buttons) pinned to the viewport (`position: sticky; height: 100vh`, so only `<main>` scrolls; the first `nav.tabs` scrolls inside it when it is too tall and the `tabs-footer` nav with the Feedback entry stays at the bottom) and stacks above the content below 800px; `.tab` / `.tab-content` / `data-tab` are what `activateTab` in `dashboard-core.js` keys on, so keep them.

**No sideways scrolling, from 360px up, on every tab.** `document.documentElement.scrollWidth` must never exceed `innerWidth`. The rules that keep it so: `.setting-row` wraps (label above, control below); controls and grids use `max-width: 100%`, `min-width: 0` or `minmax(min(Npx, 100%), 1fr)` instead of a fixed minimum; `main` sets `overflow-wrap: anywhere`, inherited, so long unbroken strings (model names, paths, file names, `<code>`, status lines) wrap and flex items shrink - do not override it; a table wider than a phone sits in a `.table-wrap` (`overflow-x: auto`) and keeps `overflow-wrap: normal`. A new row, grid or table follows the same rules. There are no UI tests: check by loading the dashboard in iframes of 360, 480, 640, 800 and 1280px in headless Edge, opening every tab, with deliberately long model names and file names in the data.

## Tabs

**Back and Forward** - the browser's history walks the pages the user visited (mouse buttons 4 and 5, Alt+Left/Right, the arrows; the browser tab the tray opens and an app window behave alike, as both keep the session history). Every step goes through `pushPage(hash)` (`dashboard-core.js`): a sidebar tab, a Settings page, an Analytics view, `goToTab`, the Meetings link into Settings, and a recording opened from elsewhere (`#recordings/<id>`, `showRecording`). The same page twice adds no entry (`samePage` compares `pageOfHash`: no hash is `#home`, a bare `#settings` is its first page, `#analytics/overview` is `#analytics`). `pushState` fires no event, so Back and Forward run `restoreTabFromHash` through `hashchange`; it opens the tab and the Settings page (a bare `#settings` shows the first page, not the one left open). `#recordings/<id>` goes through `restoreRecording` instead, which leaves the tab opening to `showRecording(id, { restore: true, current })` (one lookup, not two): coming back to the recording already chosen keeps its tab and passage, and a lookup that ends after the user moved to another entry changes nothing (`current` compares the address). A recording that is gone or an id with a malformed escape leaves `#recordings`. A hash that only corrects itself (an alias, a tab that is off) goes through `replaceHash`, which keeps the entry's marker; choosing another recording in the list rewrites `#recordings/<id>` to the new id in the same entry (no second entry), so a reload does not jump back. A reload keeps the entries and the page. Back on the first page would leave the dashboard, so on the first plain click or key press `guardHistory` turns that entry into a marker (`state.nv = "start"`) and adds a copy of it; it waits until the page start has settled the address (`markHistoryReady`), so both carry the URL the user sees, and a mouse Back button or Alt+Left does not arm it. The `popstate` handler in `dashboard-init.js` steps forward again when Back lands on the marker (the entries are added after a gesture, which browsers require for Back to stop on them). Tests: `tests/test_dashboard_history_js.py`.

**Home (first entry of the sidebar, the page the dashboard opens on)** - `#tab-home` is `.active` in the markup and so is its button; Settings no longer is. `restoreTabFromHash` (`dashboard-core.js`) opens Home when there is no hash or the hash names a tab that is off, so the same function serves the page start, the back button and a stale link; `activateTab("home")` calls `openHomeTab`. `dashboard-home.js` (loaded after `dashboard-recordings.js`, it uses `recordingTitle`, `showRecording`, `refreshMeetingStatus`, `meetingToggleBtn`, `uploadDialog`, `renderKeycapsInto`) fills: the status line `#home-status` (`describeHomeStatus`, coloured only through `setStatus`: the model name, GPU or CPU from `GET /api/device`, and "runs offline" - a custom server reads "uses your own server" instead; yellow while `GET /api/models/status` reports a switch, a download or a load, and then asked again every 3 s until it settles or Home is left; red on an error; otherwise neutral, because nothing on the page probes the Docker container or a custom server, so it never claims green); three cards - *Dictate* (not a button: it shows the current hotkey as keycaps and the hold or toggle wording), *Record a meeting* (opens Recordings, asks the app whether a meeting runs - `meetingRecording` is stale until then - and presses `#meeting-toggle` only when none does, so the consent hint still applies) and *Transcribe a file* (opens Recordings and the upload dialog; opening the tab already refreshed what the dialog shows); *Recent* (the 3 newest rows of `GET /api/file-transcriptions?limit=3`; a row opens that recording through `showRecording`, which opens the tab itself; *All recordings* opens the tab); *This week* (words dictated and time saved from `GET /api/week`, the Monday-to-Sunday report that *Your week* opens, so the numbers next to the link are the numbers behind it; *Your week* opens Analytics on its Your week view: `goToTab("analytics/week")` puts the page into the address and the tab reads it); and a tip line from the fixed `HOME_TIPS` list in the script (the first tip changes with the local day, *Next tip* steps through the list). Home has no endpoint of its own. At page start it does not repeat the Settings page's requests: `settingsReady` (the promise of `loadSettings`, which also loads the model list into `modelSpecs`) and `lastSettings` are shared state in `dashboard-core.js`; later visits ask `/api/settings` again. The keycap drawing is `renderKeycapsInto` (`dashboard-settings.js`), shared with the Settings and Meetings editors. Tested in `tests/test_home_js.py`.

**First-run setup (an overlay, `#setup`)** - Welcome, Microphone, Hotkey, Ready: a full-page `position: fixed` layer over the dashboard (`setup.css`, `dashboard-setup.js`, loaded after `dashboard-home.js`; it uses `goToTab`, `loadHomeStatus`, `startHotkeyRecording`, `saveMicrophone`, `renderKeycapsInto`). It is not a tab: no sidebar entry, no hash. While it is open `header` and `main` are `inert` and it is `role="dialog" aria-modal="true"`. It opens at page start when `GET /api/setup` says `needed` (`openSetupOnFreshInstall`, called from `dashboard-init.js` next to the other loaders; `[general].setup_done` is false only in the config a fresh install creates from the template, so existing users never see it) and from the *Run the first-run setup again* button in Settings, which dispatches `nexusvox:rerun-setup` (`openSetup` listens). *Skip setup* sits under every step; it and *Open Home* on Ready both run `endSetup`: `POST /api/setup/complete`, close, `goToTab("home")` (a failed save never traps the user; the setup then shows again at the next start). One panel per step (`.setup-panel[data-step]`, `showSetupStep`), a numbered step list above them. **Microphone**: `#setup-mic-select` (System default plus the input devices; a chosen one that is unplugged stays listed as "not connected") and a level bar `#setup-meter` (`role="meter"`) fed by polling `GET /api/setup/mic-level` every 120 ms while the step shows (a run counter drops replies from an earlier run; leaving the step stops it, and the server closes the stream by itself otherwise); green "Your microphone works" at the first level above 5 %, yellow "No sound yet" after 6 s of silence, red when the device cannot be opened. The select and the Settings > Dictation select (`#audio-device-select`) are `microphoneSelects` in `dashboard-settings.js` and always show the same choice (`[audio].device`, `docs/internals/audio-and-injection.md`). **Hotkey**: the current hotkey as keycaps and *Use other keys*, which runs the Settings recorder (`startHotkeyRecording({button, report, onSaved})`) with the setup's own button and status line; *Hold* or *Toggle* (`POST /api/settings/hotkey-mode`); *Visual*, *Audio* or *Both* (`POST /api/settings/feedback-mode`; the current mode is checked, which is *Visual* on a fresh install because the config template says `visual`; "Both" is offered too: it is a valid mode, and a user who had set it would otherwise see no option checked); each choice also updates the Settings control. The test box (`#setup-test`): dictated text is pasted at the cursor, so with the box focused it lands there like in any app; any text counts as success ("It works"), not only "Hello world", so a German speaker's "Hallo Welt" works as well. The line under it is the Home status line (`loadHomeStatus(known, element, shown)`), so a model that is still loading shows. **Ready** summarises the four choices. Tests: `tests/test_first_run_setup.py`.

**Analytics** - three views in one tab (`dashboard-analytics.js`), kept in the address like the Settings pages: `#analytics` is the *Overview*, `#analytics/week` *Your week*, `#analytics/charts` the page of every chart and table; the tab opens on the Overview (`openAnalyticsTab` reads the address, so a link, a reload and `goToTab("analytics/week")` all land on the same view; a click on the tab button keeps the view it was on). *Overview*: a range of 7, 14, 30 days (the default) or all time (the last N local days up to today, not the date filter of the charts page), four tiles (words dictated, dictations, words per minute, time saved, from `GET /api/overview`), a words-per-day bar chart (`GET /api/words-per-day`, `analytics_usage.get_words_per_day`: every day of the range listed, 0 for a quiet one; without a start it begins on the first dictation; command rows are not counted), the five busiest apps as bars (`GET /api/app-breakdown`) and a link to the charts page. *Your week*: a Monday-to-Sunday report from one call, `GET /api/week?week=<any ISO date>` (`analytics_week.get_week`; no date, an unreadable one or a future week is this week): the words of each day, days dictated, days dictated (shown as N of `days_counted`: in the current week only the days from Monday to today count, so a Saturday reads "6 of 6", a past week "N of 7"), words, dictations and time saved (all from one day-totals query, `analytics_usage.get_day_totals`, which also reads the week before for the comparison; the time-saved formula is `analytics_overview.time_saved_minutes`, shared with the overview), meetings (count and recorded seconds, `FileTranscription` rows of kind `meeting`; uploads do not count), and what was learned (`learned.total` is the larger of the week's new `DictionaryEntryRow` rows and its accepted suggestions from `LearnEventRow`: an accepted suggestion only adds an entry when its phrase is new, so it can be learned without being a new row; the five newest entries are named). `first_week` (the Monday of the oldest dictation or meeting, command rows left out like everywhere in the report) is where the *previous week* button stops; *next week* stops at the current one. The headline sentence is built by the page (`weekHeadline`: words, days, time saved and the change against the week before, 5% or more reads as more or less), so its numbers use the browser's number format like the tiles. Opening the view (Home's link, the tab, the view button) always starts at this week; only the arrows move to other weeks. Dates in queries are plain `YYYY-MM-DD` (`analytics_common.parse_day`): other ISO forms count as missing, because the date filter compares strings. The words-per-day chart names the year when the range spans more than one. The report reads existing rows only and adds no tracking. *All charts and tables* is the former Analytics page: stat cards (transcriptions, words dictated, avg WPM with min/max, avg and longest duration, transcribe time with real-time factor, release-to-text latency, translated, cleaned up, polished, voice commands (total and the three most used kinds, `analytics_overview._command_row_stats`, shared with the Polished card, over the `COMMAND_APP` rows that are no polish attempt; counts commands recognised, whether or not they worked; the kind is the action of a `[nexus] <action> ...` label (two-word actions like `snap left` stay apart), else the tag such as `assistant` or `os-control`; ties go by name), file uploads with audio hours, processing time (real-time factor) and speakers per upload, minutes saved), the totals of these cards leave out command rows (`analytics_overview._dictations`), charts (timeline, language, peak hours, latency trend, top words, heatmap; the timeline, peak hours, latency trend, accuracy trend, heatmap and the date filter (`_apply_date_filter`, by local day) are in local time through SQLite's `localtime`, and every other chart and table here leave out command rows: `_apply_date_filter` drops them unless a query asks for `commands=True`, as the command and polish cards do; the weekly buckets of the timeline, latency and accuracy charts are keyed by the Monday that starts the week, so a week over New Year is one bucket, and the page shows them as "Week of 2 Nov"; `get_words_per_day` lists at most 3660 days, the newest ones) a per-model table (`GET /api/model-breakdown`), a "Speed by model" table (`GET /api/model-speed`, `analytics_overview.get_model_speed`: per language model, server (`host:port` of `llm_url`, so one model name on two servers is two rows), level and transcription device the passes, the median model time and the share that timed out, over stored rows only; cleanup passes and polish attempts, polish as its own level and without a device (it never touches the transcriber), extensions, rows from before the columns existed and `skipped` cleanups (the model was reloading, no request was sent; they count neither in the passes, the median nor the timeout share) left out) a "Transcription speed by model" table (`GET /api/transcription-speed`, `analytics_overview.get_transcription_speed`: per transcription model (`Transcription.model`) and device the dictations, the median `transcribe_ms` and the median real-time factor `transcribe_ms / duration_ms`; dictation rows only, rows without a model or without `transcribe_ms` left out, rows from before `transcribe_device` existed under the device `unknown`; a dictation of duration 0 counts but has no factor) and a per-app table (`GET /api/app-breakdown`: dictations and words by the target app, see below). Timing comes from `transcribe_ms` / `latency_ms` on `Transcription`, both measured from the moment recording stopped; rows written before those columns existed are skipped in the averages. Each dictation row also records which model and device produced its timings: `llm_model`, `llm_url` and `cleanup_level` (`light` / `medium`; NULL for polish) come from the `CleanupResult` of the pass (set only when a request was sent: not when cleanup was off, too short or skipped because the model was reloading) or, for a polish attempt, from `[llm]` as it was when the request went out (an extension names none, also when its paste failed); `transcribe_device` (`cpu`, `gpu`, `local`, `remote`) is the transcriber's `device` attribute (`BaseTranscriber.device`: only what the app knows for sure is stored: `cpu` or `gpu` when the engine runs inside the app on that device, `local` for a server on this PC (the Docker server included: a server does not prove a GPU; loopback, `host.docker.internal`, the PC's own name or address count as this PC), `remote` for a server address that is not this PC (the custom server follows the same rule by its URL); the device is read when the transcript arrives and travels with the recording; `AutoParakeetTranscriber` sets it per cycle and to `cpu` when a take is replayed). All four are NULL on older rows, which `Database._migrate` leaves untouched. Cleanup results are `cleanup_status` (`applied`, `unchanged`, `rejected`, `timeout`, `failed`, `skipped`: the model was still reloading, no request was sent) and `cleanup_ms` on `Transcription`; polish on selected text is `polish_status` (`applied`, `failed`, `timeout`, `extension`) and `polish_ms` (model time, NULL for an extension; the card averages applied polishes only; rows with a status are kept out of every dictation statistic by `_apply_date_filter`) on the command row `App._polish_selection` saves (a tap with nothing spoken has no recording, so its row has no audio and duration 0); `analytics_overview._command_row_stats` also feeds the "Polished" card and counts older `[polish] ...` / `[extension] ...` command rows without a status as applied / extension; upload stats (`analytics_overview.get_upload_overview`, merged into `/api/overview`) cover `FileTranscription` rows of kind `upload`, with `processing_ms` timed from conversion to saving and the speaker count derived from the `words` JSON. Each typed dictation stores the process file name of the focused app at paste time (`Transcription.app`, lower-case, e.g. `outlook.exe`; never a window title; NULL for older rows, phone dictations and texts the clipboard refused, `models.COMMAND_APP` for command rows, which the per-app table leaves out; read in the executor right before the paste by `App._paste`); `analytics_usage.app_label` maps it to a friendly name from `APP_NAMES`, the file name without `.exe` for an unlisted process and "Unknown" for NULL; `get_app_breakdown` shows the `MAX_APP_ROWS` (10) busiest apps and sums the rest into "Other". Accuracy and dictionary stats (`GET /api/accuracy?period=`, one payload, rendered by `renderAccuracy`): corrections per 100 dictated words over time (`analytics_accuracy.get_accuracy_over_time`: words changed between `text` and `corrected_text` plus suggestions accepted in the dashboard, over all dictated words of the period), the most corrected phrases (`get_most_corrected`, `dictionary.suggest_entries` over reviewed rows), learn-from-edits outcomes (`get_learn_outcomes`) and per-entry dictionary use (`get_dictionary_usage`). Outcomes are stored as `LearnEventRow` rows by `EditWatcher._record` through its `on_outcome` callback (`Database.record_learn_event`; an accepted suggestion adds an `accepted` row), so they survive a restart (both stat writes run on the app's one-thread `_stats_pool`, never on the event loop or before the paste; command rows are left out of the dictated-word count, and an accepted suggestion on a day without dictation counts toward the total but has no rate), unlike the in-memory counts of `/api/settings/learn-from-edits-status`. Every application of a dictionary entry is counted per entry and local day (through SQLite's `localtime`; rows from before that hold a UTC day) in `DictionaryUsageRow` (`Database.record_dictionary_hits`, fed by `ProcessedText.dictionary_hits` from `dictionary.apply_dictionary_counted`); the key is the lower-cased `wrong` phrase, so history outlives a deleted entry (shown as removed). The `confidence` column still exists but no backend fills it (vLLM's realtime protocol sends no logprobs), so it is not shown.

**Settings****
Layout (`index.html`, `style.css`): Settings is one page per section. `.settings-layout` holds a navigation column (`#settings-nav`: `#settings-search`, one `a.settings-link[data-card]` per page with its duotone icon, and the `#settings-rerun-setup` button) and `#settings-pages` with one `.settings-card` per page, in this order (by how often they are used) - Dictation, Vocabulary, Text & Polish, Models, Meetings, Privacy, Advanced. Exactly one card has `.active` and is shown (Dictation on load: its card and link are `.active` in the markup): `showSettingsPage` in `dashboard-settings.js` switches pages, marks the open link with `.active` and `aria-current="page"`, and calls the listeners registered with `onSettingsPageOpen(fn)` (the Models page wakes the language-model refresher, the Vocabulary page redraws the learn-from-edits line; both are polled only while their page is on screen). A successful file is deselected; a failed one stays selected for another try. **Progress:** `POST /api/file-transcribe` checks the name first (extension; 400 before anything is saved), has Werkzeug store the body once, straight into a temporary file (`nexusvox-upload-*`, `_UploadSpool` through the request class's `_get_file_stream`; never read into memory, and a file with a refused extension is read from the socket and dropped, not stored; `MAX_UPLOAD_BYTES` is 2 GB, and `MAX_CONTENT_LENGTH` in `_create_app` answers a larger body with the JSON 413 `File too large (max 2 GB)`), checks its size (400) and starts a background job on that path, answering 202 `{ok, job_id}` at once; `start_file_transcription(source, ...)` owns the temporary file and removes it when the job ends or fails, or at once when the file is refused or another job runs; a quit or crash leaves the files behind, so `sweep_upload_leftovers` (a thread at dashboard API start, next to the meeting sweep) deletes every `nexusvox-upload-*` and `nexusvox-convert-*` file in the temp folder; a second upload while a job runs is a 409. `FileJobs` (`file_jobs.py`, one per `DashboardAPI`, in memory, last 10 finished jobs kept, one running job at a time, no queue) runs `upload_and_transcribe(job=)` on a daemon thread; the stage comes from `FileJob.update(stage, current, total)`: `converting`, `transcribing` (chunk i of n, from `transcribe_file(on_progress=)`), `diarizing` (only when the chunks are done and speaker detection still runs), `cleaning` (passage i of n, only with text cleanup) and `saving`. `GET /api/file-transcribe/<job_id>` returns `{job_id, filename, state: running|done|error, stage, current, total, message, percent (0..1), result, error}`: `result` is what the upload returned (`id`, `text`, `notes`, ...), `error` the message of a failed one (conversion, transcription, saving; a failed save is `Saving the transcript failed: ...`; any other exception in the worker is `Unexpected error: ...`). `GET /api/file-transcribe/current` returns `{job}`: the latest job while it runs, or when it ended and no client has read how yet (reading a finished job through either endpoint marks it read, atomically under the job's lock, so of two clients exactly one gets the unread outcome), else `{job: null}`. The JS (`trackUploadJob`) polls the job every second (a failed poll is retried 5 times in a row, then the page says it lost contact and the job runs on), shows `#upload-status-text` (file name and stage) and the `#upload-progress-bar`, and on done/error shows the note, the error or the refreshed history as before; `resumeUploadJob` runs when the tab opens, when the page becomes visible again and every 3 s while the Upload tab is shown and no job is tracked, so a page reloaded mid-job, or a job started from another browser tab, shows up (and the Transcribe button stays disabled), and one that ended meanwhile shows its note or error once. A job keeps running when the page is closed, the app's exit ends it. The test database must be a file, not `:memory:`: the worker thread opens its own connection. Conversion + transcription logic in `transcription/file_transcribe.py`: `convert_to_wav(path)` decodes packet by packet with PyAV (the FFmpeg inside the wheel: every format, no ffmpeg on PATH; the format comes from the content, not the name; a damaged packet is skipped, a file that is no audio is a `ValueError`) and resamples with FFmpeg's filtered resampler into a temporary 16 kHz mono WAV, and returns a `WavChunks`, a list-like of the 60 s WAV chunks (to avoid GPU OOM) read from that file one at a time and deleted by `close()` / the `with` block (a delete that fails, a scanner holding the file, is logged and never fails the job), so peak memory does not grow with the length of the file; speaker detection is skipped above `MAX_DETECTION_S` (2 h) with the note `Speaker detection skipped: the recording is longer than 2 hours; ...`: `upload_and_transcribe` decides before `speaker_detection_job`, so no model switch or Parakeet container starts for it (the whole file goes in one request and is held once as one WAV, ~115 MB per hour); results in `file_transcriptions` SQLite table (`FileTranscription` model in `storage/models.py`). No voice commands or text injection for file transcriptions. With Parakeet (`word_timestamps` in `MODEL_REGISTRY`) an upload also asks the server for per-word timing; `transcribe_file(..., word_timestamps=True)` (only the upload passes it; Review Retry does not) shifts each chunk's words by the real length of the audio before it, the joined list is stored as JSON in `file_transcriptions.words` (NULL for other engines), and a chunk that timed out or came back without words is logged and returned as `notes` in the job's `result`, which the upload tab shows in its own non-error `#upload-note` box (the upload is saved); Review Retry saves nothing, so a note there fails the retry with the note as the error. A *Detect speakers* toggle between the drop zone and the button (off by default) adds `diarize=1` to the upload FormData; `refreshDiarizeToggle` reads `diarization` from `GET /api/models/current` when the tab opens, when the page becomes visible again and right before each upload (the model can change in another browser tab or the config), and disables the toggle otherwise, with the hint "Requires <names from `diarization_models`> as the active model". A checked toggle is still sent when the model changed meanwhile, so the job's note says why there are no speakers. The flag goes through `upload_and_transcribe(diarize=)` to `transcribe_file`; the labelled `Speaker N: ...` paragraphs are the saved `text` (shown as timed speaker lines on the Transcript tab) and each stored word gets `speaker`. A problem with speaker detection is a note, the upload still saves. A *Clean up text* toggle with a Light/Medium select (`#upload-cleanup-toggle`, `#upload-cleanup-level`, off by default, read at the click) adds `cleanup=light|medium` to the FormData; anything else is no cleanup. After transcription `upload_and_transcribe(cleanup_level=)` runs `file_cleanup.clean_transcript` over the transcript (see `transcription.md`, Upload Cleanup): `text` and the word timings stay as transcribed, the cleaned text goes into `file_transcriptions.cleaned_text` (+ `cleanup_level`; both NULL when cleanup was off or changed nothing; added by the migration in `Database._migrate`). `GET /api/file-transcriptions` and the job's `result` carry `cleaned_text`; the Transcript tab shows the cleaned text by default and a *Show original* / *Show cleaned* button (`.rec-view-switch`) flips it. This cannot be undone." with Delete / Cancel in the pane (`askDeleteRecording`, never `confirm()`; the next recording in the list takes its place), then `DELETE /api/file-transcriptions/<id>` removes the row and the audio files (an upload's stored audio, a meeting's whole folder; a missing file does not block it; 404 for an unknown id, 500 with `error` when a file cannot be removed). **Rename:** the pencil next to the title (`.rec-rename`) or *Rename* in the More menu (`editFileTitle`): click opens a text field, Enter saves, Esc or blur cancels. `PATCH /api/file-transcriptions/<id>` with `{"title"}` sets `file_transcriptions.title` (trimmed, max 255, 400 beyond; empty clears it; 404 for an unknown id). `original_filename` never changes (it finds a meeting's folder and tells which folders have a transcript); the list payload carries `title`, the list, the detail pane and the export download name show it when set.

**Feedback (own tab, last entry of the sidebar, separate from the others)** - `<nav class="tabs tabs-footer">` holds the `#feedback-tab-button` (`data-tab="feedback"`), independent of the Settings tab; the button and `#tab-feedback` are `hidden` until `GET /api/settings` carries a `feedback_url` (built by `src/nexusvox/system/feedback_form.py` from `[support].feedback_form_url`, defaults to `https://nexusvox.app/feedback`; empty = no entry). The tab is a short form (`system/feedback_send.py`, `dashboard-feedback.js`): kind (`#feedback-kind`: bug, wish, other), message (`#feedback-message`, 3 to 5,000 characters) and *Include log* (`#feedback-include-log`, off by default). *Send* (`#send-feedback`) is the only thing that sends: `POST /api/feedback/send` makes the app post JSON (`kind`, `message`, `app_version`, `windows_version`, `hardware` and, with the box ticked, `log`) to `/api/app-feedback` on the host of `feedback_form_url`, with the `NexusVox/<version>` User-Agent and no Origin header; no file picker, no other request. *Show what will be sent* (`#feedback-preview-toggle`) asks `POST /api/feedback/preview` for the same report as text and refreshes while the inputs change (the page ignores a reply to an older request); the reply carries a token, and while the preview is open *Send* posts that held report (`token` in the body) instead of building a new one, so a log that grew since is not sent unseen; a Send with out-of-date inputs sends nothing (`stale`, 409) and refreshes the preview. The in-app form exists only when `GET /api/settings` has `feedback_app_send`: the form URL must be https on `nexusvox.app` or `www.nexusvox.app` (`app_feedback_url`, `APP_FEEDBACK_HOSTS`); for any other form URL only the web form is offered, so a log never goes to a third party. A lone surrogate in the message is replaced before it is shown or sent. The log is the last 300 lines (at most 50,000 characters) of today's `nexusvox.log` from the file's first start mark on (so a restart keeps the session before it; the result is cached until the file changes), with everything `logsetup` fenced as dictated text replaced by `[dictated text removed]` (full-text logging on or off) and the Windows user name in paths (also with spaces, UNC and `/c/Users/` forms) replaced by `<user>`; a file without a start mark yields no log. Success clears the message and unticks *Include log*. Success clears the message; failure, a refusal (rate limit, daily cap, too large) and no connection each show their own red line and keep the text. *Open the web form* (`#open-feedback-form`, `window.open`) stays as the fallback, and the support address `nexusvox@nightshift-ai.de`. The app stays fully usable offline: nothing is requested until the click.

**Extension tabs** - an installed extension (`extensions.md`; contract in `docs/EXTENSIONS.md`) may add tabs and export links. On `DOMContentLoaded` `loadExtensions()` reads `GET /api/extensions`, appends a `.tab` button (`data-tab="ext-<id>"`) and an empty `.tab-content` section per panel (`bindTab` wires the click, `activateTab` calls `openExtensionPanel`), and keeps the export targets and upload actions for the Recordings detail pane, where each recording gets an *Export* menu entry per target (`.rec-export`) and a More-menu entry per action; the hash restore waits for it. The panel's script is added on first open of its tab, and draws through `NexusVoxExt.registerPanel(id, container => ...)`. With nothing installed the page shows no extra tab; the built-in TXT/SRT/VTT export links are always there, so a non-empty `exports` list does not mean an extension is installed. An export or upload action with an `available` check is greyed out with its reason shown under it (`exports_unavailable` / `actions_unavailable` per row), and `text`/`cleaned_text` in the list pass through the extensions' `display_text` hook (the job `result` and the stored row stay raw). A state dict instead of a string (`{pending}` / `{error, retry}`) shows a spinner line or the reason with a Retry button under the detail pane's head; while the list has a pending row, `loadFileTranscriptions(true)` reloads it every 4 s (`createPendingPoller`; paused while the page is hidden or the Recordings tab is not shown, resumed on `visibilitychange`), the newest load wins (`recLoadGeneration`), and a poll that brings the chosen recording unchanged leaves the detail pane alone. SRT/VTT are greyed out (`exports_unavailable`, with `NO_TIMING_HINT` under them) for a row without stored word timing; TXT is the text as shown (cleaned when cleanup ran) while the subtitles use the words as transcribed. The panel blueprints are mounted by `_create_app` (a mount failure is logged, the dashboard stays up), and `upload_and_transcribe` adds `extensions` (per-extension results, `{}` when none) to the job `result`.

**Review**** — unreviewed recordings that have audio files, oldest first. Each card has *Retry* (`POST /api/review/<tid>/retry`): the stored WAV is transcribed again with the current model (same path as file upload, `transcribe_file`) and the result goes into the correction box; nothing is saved until the user submits. It needs the WAV, i.e. `[database].store_audio`, which the tab says. Users confirm correctness via checkbox or provide corrected text. Flagged-but-unreviewed items highlighted red with checkbox defaulting to incorrect. `reviewed` column on `Transcription` is tri-state: `0`=unreviewed, `1`=correct, `2`=incorrect.

**Dev (experimental: `[experimental].dev_tab`)**** — hidden and its `/api/benchmarks*` routes not registered unless the flag is on (`?dev` does nothing). Reads benchmark JSON files from `benchmarks/` directory. Two views: comparison mode (table + WER bar chart + RTF bar chart across all benchmarks) and detail mode (WER distribution histogram, latency scatter plot, sample explorer with word-level diff). WER targets from roadmap: EN <8%, DE <12%. Orange accent distinguishes from production tabs. Backend logic in `benchmarks.py`.
