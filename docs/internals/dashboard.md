# Dashboard internals

The Flask server, its modules, the look and every tab. Rules: `src/nexusvox/dashboard/CLAUDE.md`. Endpoint list: `docs/internals/dashboard-api.md`. Module paths such as `app/core.py` are relative to `src/nexusvox/`; paths that start with a top-level folder (`tests/`, `docs/`, `docker/`, `scripts/`) are from the repository root.

## Server

Flask server starts once on first tray click (left-click on the icon or the Dashboard menu item), runs in a daemon thread on `127.0.0.1:47392`; when another program holds that port, `_bind_server` binds the first free one of `_FALLBACK_PORTS` (47400-47409; 47393 is the remote mic) on a socket of its own (exclusive on Windows, `SO_EXCLUSIVEADDRUSE`; werkzeug exits the process when its own bind fails, so it gets the socket as `fd`) and `open_dashboard` opens that (`_port`), and with every port held it logs an error and shows a message box (`single_instance.show_message`) instead of opening a dead tab; that failure is remembered (`_start_failed`), so later calls neither re-probe nor build a second `DashboardAPI`. Static files in `src/nexusvox/dashboard/static/` (HTML, CSS, JS, bundled Chart.js — no CDN). API endpoints under `/api/*` return JSON, consumed by vanilla JS `fetch()` calls.

The page's JavaScript is one file per tab plus shared helpers, flat in `static/` (`pyproject.toml` packages `dashboard/static/*`), loaded by `index.html` in this fixed order: `dashboard-core.js` (fetch guard, `setStatus`, theme, `api`, feature flag state, tab switching, `NexusVoxExt`, shared helpers), `dashboard-settings.js`, `dashboard-feedback.js` (the Feedback tab's form), `dashboard-settings-models.js`, `dashboard-settings-vocabulary.js`, `dashboard-analytics.js`, `dashboard-edit.js`, `dashboard-review.js`, `dashboard-upload.js` (also the transcript cards the Meetings tab shares), `dashboard-meetings.js`, `dashboard-dev.js`, `dashboard-init.js` (feature flag loading, the tab and `hashchange` wiring and the `DOMContentLoaded` loaders, last, so no tab goes live before the files its handlers call have run). They are classic scripts sharing one global scope, not modules, so extension panels and inline handlers reach the same names as before. A function is hoisted only within its own file: top-level code may use only what its own or an earlier file defines, while anything inside a handler or a function called after load can use every file. `escapeHtml` escapes quotes too, so its result is safe in a quoted attribute. `test_dashboard_scripts.py` pins the order and runs the files together under Node against a stand-in page built from the ids in `index.html`. Tests read them through `tests/dashboard_js.py`, joined in load order; `scripts.py` (`page_scripts`) is the one reader of the script tags, shared with both packaging checks.

- `guard.py` — access control, one `before_request` hook installed first in `_create_app`, so every route (extension blueprints included) is covered: the Host header must be `127.0.0.1`/`localhost` with the dashboard port (DNS rebinding), an `Origin` header must be one of those origins, `Sec-Fetch-Site` must be `same-origin` or `none`, and every request needs the `HttpOnly`, `SameSite=Strict` session cookie (random per run) or gets 403 (JSON with an `X-NexusVox-Denied` header for `/api/*`, which a `fetch` wrapper at the top of `dashboard-core.js` turns into a reopen-from-tray banner). The cookie comes from `GET /?launch=<secret>`: `open_dashboard` builds that URL with a single-use secret (60 s TTL) held in memory; the server is bound before `_server_started` is set, and a busy port opens no browser, so a program that only requests `/` gets nothing. After a restart an old tab is refused until it is reopened from the tray. Tests: `test_dashboard_guard.py`; `tests/conftest.py` makes every `app.test_client()` signed in.
- `analytics.py` — the one import path for the SQLAlchemy query functions, which live in `analytics_*.py`, one module per topic: `analytics_overview` (overview cards, polish and command rows, uploads), `analytics_usage` (charts over time, languages, words, models, apps), `analytics_accuracy` (corrections, learn outcomes, dictionary use), `analytics_review` (the flagged and review lists) and `analytics_common` (`_apply_date_filter`). A new public query goes into its topic module and is re-exported here; `tests/test_analytics_exports.py` pins the names. Private helpers stay in their module
- `api.py` — `DashboardAPI`: joins the topic mixins below and owns the state they share (`__init__`). The Flask routes that call it are in `routes_*.py`
- `api_base.py` — the shared `logger` (every topic module imports it, so all log as `nexusvox.dashboard.api`) and `DashboardState`, the base of every mixin: it declares the state and the methods of other mixins a mixin may use, and holds `_db_dir`. A mixin that uses something new of another one declares it there; `tests/test_dashboard_api_contract.py` fails otherwise, and on a declared name that is gone or unused, since no type checker runs here. `MeetingsMixin` and `MeetingTranscriptMixin` use each other: they are two halves of one topic
- `api_*.py` — the mixins, one per topic: `api_models` (models, device), `api_settings` (settings page, language model), `api_commands` (voice and OS commands), `api_analytics` (statistics, benchmarks), `api_review` (flagged, review), `api_vocabulary` (dictionary, polish presets), `api_files` (uploads and the rows uploads and meetings share), `api_meetings` (recording, pending meetings, meeting settings), `api_meeting_transcript` (the transcription job). A test patches a name in the module that uses it. A name several modules import has a copy in each, and a patch on one does not reach the others: `save_config` (use the `no_config_save` fixture), `cuda_available` and `convert_to_wav` (use `patch_api(name, value)`, which replaces every copy)
- `routes_*.py` — the Flask routes, one module per topic, matching the mixins: `routes_models`, `routes_settings`, `routes_meetings` (also `/api/settings/meeting-*`), `routes_commands`, `routes_analytics` (also the benchmarks), `routes_review`, `routes_vocabulary`, `routes_files` and `routes_extensions`; `routes_base` holds `_switch`. Each has a `register(app, api)`, and `_create_app` calls them through `_ROUTE_MODULES`; `tests/test_dashboard_routes.py` fails when a module is left out. Modules with flag-gated routes read `api.experimental` there, at start. Routes go straight on the app with `@app.route`: a blueprint would rename every endpoint. `routes_extensions` logs as `nexusvox.dashboard`, the name its lines always had (`tests/test_extensions.py` pins it). `__init__.py` keeps `_create_app`, `/`, `/api/features` and the server code, because tests patch `_make_server`, `_PORT` and `show_message` there
- `benchmarks.py` — benchmark JSON file I/O and cross-model comparison (Dev tab, experimental)
- `file_jobs.py` — in-memory registry of file transcription jobs (Upload tab progress)

## Look

**Status colour rule (every status line, hint and badge).** Green (`.status-line.ok`) = works as expected ("Model server reachable"). Yellow (`.status-line.warn`, `.badge.warn`, token `--yellow`) = works, but with a caveat the user should know: slower on the CPU (the Cleanup latency hint), Experimental/Beta, Alt in the dictation or meeting hotkey (`renderAltHint`, `#hotkey-alt-hint` / `#meeting-hotkey-alt-hint`, shown and cleared live), a fallback is active (speech engine "Auto" resolved to the CPU; a GPU asked for explicitly without CUDA is red). Red (`.status-line.down`) = does not work or is not reachable ("No translator"). No class = neutral (checking, idle). JS sets the state only through `setStatus(el, state, text)` (state `"ok"`, `"warn"`, `"down"`, anything else is neutral; it touches only the state classes, so other classes on the element stay; an HTML template leaves the state class out and calls `setStatus` when it shows the line); static hints that are always a caveat carry `status-line warn` in the HTML. Do not add a new colour or write `status-line` class names by hand. The dashboard has one (dark) theme, so the tokens in `style.css` are the single place to adjust contrast; `tests/test_status_colours.py` covers the rule.

Aurora Precision theme, shared with the website. Tokens are the `:root` variables in `style.css` (`--bg`, `--surface*`, `--border*`, `--text*`, `--accent`/`--accent-light`, `--green`, `--yellow`, `--red` (status colours, see below), `--orange` (only the Dev tab's identity, never a status), 18px cards); `COLORS` at the top of `dashboard-core.js` reads them (and the font) from the computed style at startup for Chart.js, so `style.css` is the only place to change a color; chart-only tints are the `--accent-soft`, `--accent-fill` and `--green-fill` tokens. Geist and Geist Mono (SIL OFL) are bundled flat in `static/` (`Geist-Variable.woff2`, `GeistMono-Variable.woff2`, license in `Geist-OFL.txt`; `pyproject.toml` packages `dashboard/static/*`, so they must stay flat) - no CDN, the dashboard works offline. The `<header>` is a left sidebar (brand + stacked `.tab` buttons) pinned to the viewport (`position: sticky; height: 100vh`, so only `<main>` scrolls; the first `nav.tabs` scrolls inside it when it is too tall and the `tabs-footer` nav with the Feedback entry stays at the bottom) and stacks above the content below 800px; `.tab` / `.tab-content` / `data-tab` are what `activateTab` in `dashboard-core.js` keys on, so keep them.

**No sideways scrolling, from 360px up, on every tab.** `document.documentElement.scrollWidth` must never exceed `innerWidth`. The rules that keep it so: `.setting-row` wraps (label above, control below); controls and grids use `max-width: 100%`, `min-width: 0` or `minmax(min(Npx, 100%), 1fr)` instead of a fixed minimum; `main` sets `overflow-wrap: anywhere`, inherited, so long unbroken strings (model names, paths, file names, `<code>`, status lines) wrap and flex items shrink - do not override it; a table wider than a phone sits in a `.table-wrap` (`overflow-x: auto`) and keeps `overflow-wrap: normal`. A new row, grid or table follows the same rules. There are no UI tests: check by loading the dashboard in iframes of 360, 480, 640, 800 and 1280px in headless Edge, opening every tab, with deliberately long model names and file names in the data.

## Tabs

**Analytics**** — stat cards (transcriptions, words dictated, avg WPM with min/max, avg and longest duration, transcribe time with real-time factor, release-to-text latency, translated, cleaned up, polished, voice commands (total and the three most used kinds, `analytics_overview._command_row_stats`, shared with the Polished card, over the `COMMAND_APP` rows that are no polish attempt; counts commands recognised, whether or not they worked; the kind is the action of a `[nexus] <action> ...` label (two-word actions like `snap left` stay apart), else the tag such as `assistant` or `os-control`; ties go by name), file uploads with audio hours, processing time (real-time factor) and speakers per upload, minutes saved), the totals of these cards leave out command rows (`analytics_overview._dictations`), charts (timeline, language, peak hours, latency trend, top words, heatmap; the timeline, peak hours, latency trend, accuracy trend, heatmap and the date filter (`_apply_date_filter`, by local day) are in local time through SQLite's `localtime`, top words leaves out command rows) a per-model table (`GET /api/model-breakdown`) and a per-app table (`GET /api/app-breakdown`: dictations and words by the target app, see below). Timing comes from `transcribe_ms` / `latency_ms` on `Transcription`, both measured from the moment recording stopped; rows written before those columns existed are skipped in the averages. Cleanup results are `cleanup_status` (`applied`, `unchanged`, `rejected`, `timeout`, `failed`) and `cleanup_ms` on `Transcription`; polish on selected text is `polish_status` (`applied`, `failed`, `timeout`, `extension`) and `polish_ms` (model time, NULL for an extension; the card averages applied polishes only; rows with a status are kept out of every dictation statistic by `_apply_date_filter`) on the command row `App._polish_selection` saves (a tap with nothing spoken has no recording, so its row has no audio and duration 0); `analytics_overview._command_row_stats` also feeds the "Polished" card and counts older `[polish] ...` / `[extension] ...` command rows without a status as applied / extension; upload stats (`analytics_overview.get_upload_overview`, merged into `/api/overview`) cover `FileTranscription` rows of kind `upload`, with `processing_ms` timed from conversion to saving and the speaker count derived from the `words` JSON. Each typed dictation stores the process file name of the focused app at paste time (`Transcription.app`, lower-case, e.g. `outlook.exe`; never a window title; NULL for older rows, phone dictations and texts the clipboard refused, `models.COMMAND_APP` for command rows, which the per-app table leaves out; read in the executor right before the paste by `App._paste`); `analytics_usage.app_label` maps it to a friendly name from `APP_NAMES`, the file name without `.exe` for an unlisted process and "Unknown" for NULL; `get_app_breakdown` shows the `MAX_APP_ROWS` (10) busiest apps and sums the rest into "Other". Accuracy and dictionary stats (`GET /api/accuracy?period=`, one payload, rendered by `renderAccuracy`): corrections per 100 dictated words over time (`analytics_accuracy.get_accuracy_over_time`: words changed between `text` and `corrected_text` plus suggestions accepted in the dashboard, over all dictated words of the period), the most corrected phrases (`get_most_corrected`, `dictionary.suggest_entries` over reviewed rows), learn-from-edits outcomes (`get_learn_outcomes`) and per-entry dictionary use (`get_dictionary_usage`). Outcomes are stored as `LearnEventRow` rows by `EditWatcher._record` through its `on_outcome` callback (`Database.record_learn_event`; an accepted suggestion adds an `accepted` row), so they survive a restart (both stat writes run on the app's one-thread `_stats_pool`, never on the event loop or before the paste; command rows are left out of the dictated-word count, and an accepted suggestion on a day without dictation counts toward the total but has no rate), unlike the in-memory counts of `/api/settings/learn-from-edits-status`. Every application of a dictionary entry is counted per entry and local day (through SQLite's `localtime`; rows from before that hold a UTC day) in `DictionaryUsageRow` (`Database.record_dictionary_hits`, fed by `ProcessedText.dictionary_hits` from `dictionary.apply_dictionary_counted`); the key is the lower-cased `wrong` phrase, so history outlives a deleted entry (shown as removed). The `confidence` column still exists but no backend fills it (vLLM's realtime protocol sends no logprobs), so it is not shown.

**Settings****
Layout (`index.html`, `style.css`): one `.settings-card` per group, in this order (by how often they are used) - Dictation, Vocabulary, Text & Polish, Models, Meetings, Privacy, and a collapsed `<details id="settings-advanced">`. The sidebar shows a `.subtabs` submenu (`#settings-submenu`, one `a.subtab[data-card]` per card, only while the Settings tab is active; click scrolls to the card and opens Advanced; the entry of the card in view is highlighted on scroll) and `#settings-search` at the top of the tab filters the direct children of each card (rows, sub-blocks, hints) by their visible label and hint text - not option lists, buttons, hidden parts or user lists (cards without a match get `.search-hidden`, a match in Advanced opens it, Esc clears, "No setting found" when empty). Smaller blocks are `.settings-sub` blocks inside their group (indented one level deeper than the group's rows). Every control keeps its element id; a new setting goes into the group a user would look in, only rarely used ones into Advanced. Where things live: Dictation = hotkey, mode, feedback, mute other apps; Text & Polish = paste key, polish key, auto cleanup, translate, voice commands; Vocabulary = dictionary, polish presets; Models = model select + overview; Privacy = store audio, log folder, log full text; Advanced = compute device, polish in terminals, polish model, Nexus OS commands.
- Dictation, Text & Polish, Privacy and Advanced controls: Hotkey editor (keycap display of the current binding with a `default`/`custom` badge, the default named in the text, modifier checkboxes + key select, a *Reset to default* button (disabled while on the default, `hotkey_default` in `GET /api/settings`) and a *Record* button that captures the next combo pressed in the page via `KeyboardEvent.code`; a modifier-only combo is taken on the first key-up), `POST /api/settings/hotkey` with `{modifiers: [...], key: ""}` (400 with `error` on an unusable binding, canonical modifier order and upper-case key in the reply); Hotkey Mode select (`hold` / `toggle`), `POST /api/settings/hotkey-mode`; Paste Last Text Key select (`Off` or any hotkey key name, `paste_key` in `GET /api/settings`), `POST /api/settings/paste-key` with `{key}` (400 on an unknown key, the hotkey's own key, the enabled os-control command key, or the polish key - the listener would ignore or misread those); Polish Selected Text Key select (`polish_key`, `POST /api/settings/polish-key`, same checks against the paste key) with an LLM status line (`GET /api/settings/llm-status`, probed live like the translator), a Polish In Terminals Too toggle (`polish_in_terminals`, `POST /api/settings/polish-terminals`, `[polish].in_terminals`) an Auto Cleanup select (`cleanup_level`, `cleanup_levels`, `POST /api/settings/cleanup-level` with `{level}`, 400 on an unknown level; switching it on warms the model up in the background); Ollama install hints (`ollamaHint`, `renderOllamaHint`, `renderModelsHint`, `renderLlmHints` in `dashboard-settings-models.js`, pure and tested under Node in `test_ollama_hint_js.py`): one `llm-status` reply drives four red lines through `setStatus()` - `#llm-status` (Polish, only with a polish key), `#cleanup-llm-hint` (only with Cleanup not Off), `#upload-llm-hint` (only with the upload *Clean up text* toggle on) and `#llm-model-hint` (Models card) - each hidden when the feature is off or all is well. Unreachable local Ollama links to ollama.com/download, a remote `[llm].url` shows the address instead, a missing model points to Settings > Models, where `#llm-pull-selected` downloads the saved model (selecting it again fires no `change`). They poll on their own every 5 s while Settings or Upload is open (not through the model list refresher), on tab entry and when the page becomes visible; every toggle re-renders from the cached reply. the Dictation feedback select: a Sound / Visual / Sound and visual select (`feedback_mode`, `feedback_modes` in `GET /api/settings`, `POST /api/settings/feedback-mode` with `{mode}`, 400 on an unknown mode, `[feedback].mode`, live; see `audio-and-injection.md`, Dictation Feedback); the Mute Other Apps While Recording toggle, `POST /api/settings/mic-guard`, and the Store Audio Recordings toggle, `POST /api/settings/store-audio` (`[database].store_audio`). All live: `HotkeyListener` reads the shared `Config` on every key event and `app/events.py` checks `[mic_guard].enabled` on every hold, no restart and no app bridge needed.
- Compute Device dropdown (Advanced) (`Auto`/`GPU (CUDA)`/`CPU`): writes `[inference].device` to `config.toml`; requires app restart. On CPU, GPU-only models are filtered out of the model dropdown server-side.
- Model switcher dropdown (Models): for GPU-backed models, selecting stops the old Docker container, starts the new one, waits for health check, reconnects the transcriber. For in-process models (Whisper, Parakeet on CPU), just reloads the model — no Docker calls. - Voice Commands (Text & Polish): master enable/disable toggle; Numbers as Digits toggle; Press Enter Command toggle (`POST /api/voice-commands/press-enter`); Bypass Structural Commands toggle + structural command chips (`new line`, `new paragraph`, `tab`, `all caps`; `POST /api/voice-commands/structural`); Bypass Symbol Commands toggle + symbol command chips (click to activate/deactivate individual symbols, persisted immediately via `POST /api/voice-commands/symbols`).

**Edit (experimental: `[experimental].flag_command`)**** — flagged transcriptions with editable correction textarea and audio playback. Saves via `POST /api/flagged/<id>/correct`. Audio served via `GET /api/audio/<tid>`.

**Meetings**** — Start/Stop button with a timer (`GET /api/meetings/status` every 3 s while the tab is shown, the page counts seconds in between) and a red indicator; Start shows the in-page consent hint ("Inform all participants before you record", *Don't show this again* sets `[meeting].consent_hint` off; never a browser dialog) unless it is off; Stop (`POST /api/meetings/stop`) starts the transcription job and the tab polls `GET /api/file-transcribe/<job_id>` for the progress bar. Meeting hotkey editor (modifier checkboxes + key, `POST /api/settings/meeting-hotkey`, 400 with `error` on an unusable one), microphone and output device selects (`GET /api/meetings/devices`, `POST /api/settings/meeting-devices`, empty = system default), consent hint toggle (`POST /api/settings/meeting-consent-hint`), *Leave dictation out of the meeting transcript* toggle (`POST /api/settings/meeting-leave-dictation-out`, `meeting_leave_dictation_out` in `GET /api/settings`, `[meeting].leave_dictation_out`), *Store meeting audio* toggle (`POST /api/settings/meeting-store-audio`, `meeting_store_audio`, `[meeting].store_audio`, default on: `meeting.wav` is kept after a successful transcription; off deletes it too; the per-track WAVs are always deleted then; a row without audio has no player). *Live transcript* box under the timer (`#meeting-live`, polled every 2 s by `GET /api/meetings/live?after=<n>` (one request in flight, segments below the shown `n` skipped, a generation counter drops a response from a previous meeting) until the meeting is over and the worker has ended, also when it was stopped from another tab, text only via `textContent`; own-voice label / `Others` labels (live only), a model-load line and a note when audio was skipped) and the *Show a live transcript while recording* toggle (`POST /api/settings/meeting-live-transcript`, `meeting_live_transcript` in `GET /api/settings`, `[meeting].live_transcript`, off by default, from the next meeting). *Recorded, not yet transcribed* (`GET /api/meetings/pending`, hidden when empty) lists recordings without a transcript with Transcribe (`POST /api/meetings/pending/<name>/transcribe`, 409 while another file is transcribing) and Delete (`DELETE /api/meetings/pending/<name>`, in-card confirmation; only folders `meeting-*` holding `meeting.json` that are neither recording nor transcribing, else 404). The progress poll treats a vanished job (404) as lost contact, never as success. An upload action or export started from a Meetings card reports its error and note in `#meeting-error` / `#meeting-note` of the Meetings tab (`feedbackEls`, keyed on the card's tab), never in the hidden Upload tab's `#upload-error`. *Previous Meetings* is the file-transcription list narrowed to `?kind=meeting` (audio player, Delete). See `meetings.md`, Meeting Session.

**Upload**** — drag-and-drop file upload (WAV, MP3, FLAC, OGG, WebM; max 25 MB) with transcription history list. Choosing or dropping a file only selects it (`selectUploadFile`): the drop zone turns solid green with "Ready to transcribe" (`.has-file`) and `#upload-selected` shows a row with the file name, size and, once the browser has read its metadata, the duration, plus a remove button (`#upload-remove`, disabled while a job runs, which also ignores a new pick or drop; focus moves to *browse* afterwards) that restores the empty state; the *Transcribe* button (`#upload-transcribe`) starts a job, is disabled until a file is selected and while a job runs (`uploadRunning`), and the options are read at the click. A successful file is deselected; a failed one stays selected for another try. **Progress:** `POST /api/file-transcribe` only checks the file (extension, size; 400 on a bad one) and starts a background job, answering 202 `{ok, job_id}` at once; a second upload while a job runs is a 409. `FileJobs` (`file_jobs.py`, one per `DashboardAPI`, in memory, last 10 finished jobs kept, one running job at a time, no queue) runs `upload_and_transcribe(job=)` on a daemon thread; the stage comes from `FileJob.update(stage, current, total)`: `converting`, `transcribing` (chunk i of n, from `transcribe_file(on_progress=)`), `diarizing` (only when the chunks are done and speaker detection still runs), `cleaning` (passage i of n, only with text cleanup) and `saving`. `GET /api/file-transcribe/<job_id>` returns `{job_id, filename, state: running|done|error, stage, current, total, message, percent (0..1), result, error}`: `result` is what the upload returned (`id`, `text`, `notes`, ...), `error` the message of a failed one (conversion, transcription, saving; a failed save is `Saving the transcript failed: ...`; any other exception in the worker is `Unexpected error: ...`). `GET /api/file-transcribe/current` returns `{job}`: the latest job while it runs, or when it ended and no client has read how yet (reading a finished job through either endpoint marks it read, atomically under the job's lock, so of two clients exactly one gets the unread outcome), else `{job: null}`. The JS (`trackUploadJob`) polls the job every second (a failed poll is retried 5 times in a row, then the page says it lost contact and the job runs on), shows `#upload-status-text` (file name and stage) and the `#upload-progress-bar`, and on done/error shows the note, the error or the refreshed history as before; `resumeUploadJob` runs when the tab opens, when the page becomes visible again and every 3 s while the Upload tab is shown and no job is tracked, so a page reloaded mid-job, or a job started from another browser tab, shows up (and the Transcribe button stays disabled), and one that ended meanwhile shows its note or error once. A job keeps running when the page is closed, the app's exit ends it. The test database must be a file, not `:memory:`: the worker thread opens its own connection. Conversion + transcription logic in `transcription/file_transcribe.py`; 60-second chunking to avoid GPU OOM; results in `file_transcriptions` SQLite table (`FileTranscription` model in `storage/models.py`). No voice commands or text injection for file transcriptions. With Parakeet (`word_timestamps` in `MODEL_REGISTRY`) an upload also asks the server for per-word timing; `transcribe_file(..., word_timestamps=True)` (only the upload passes it; Review Retry does not) shifts each chunk's words by the real length of the audio before it, the joined list is stored as JSON in `file_transcriptions.words` (NULL for other engines), and a chunk that timed out or came back without words is logged and returned as `notes` in the job's `result`, which the upload tab shows in its own non-error `#upload-note` box (the upload is saved); Review Retry saves nothing, so a note there fails the retry with the note as the error. A *Detect speakers* toggle between the drop zone and the button (off by default) adds `diarize=1` to the upload FormData; `refreshDiarizeToggle` reads `diarization` from `GET /api/models/current` when the tab opens, when the page becomes visible again and right before each upload (the model can change in another browser tab or the config), and disables the toggle otherwise, with the hint "Requires <names from `diarization_models`> as the active model". A checked toggle is still sent when the model changed meanwhile, so the job's note says why there are no speakers. The flag goes through `upload_and_transcribe(diarize=)` to `transcribe_file`; the labelled `Speaker N: ...` paragraphs are the saved `text` (shown with `white-space: pre-wrap`, `.upload-text`) and each stored word gets `speaker`. A problem with speaker detection is a note, the upload still saves. A *Clean up text* toggle with a Light/Medium select (`#upload-cleanup-toggle`, `#upload-cleanup-level`, off by default, read at the click) adds `cleanup=light|medium` to the FormData; anything else is no cleanup. After transcription `upload_and_transcribe(cleanup_level=)` runs `file_cleanup.clean_transcript` over the transcript (see `transcription.md`, Upload Cleanup): `text` and the word timings stay as transcribed, the cleaned text goes into `file_transcriptions.cleaned_text` (+ `cleanup_level`; both NULL when cleanup was off or changed nothing; added by the migration in `Database._migrate`). `GET /api/file-transcriptions` and the job's `result` carry `cleaned_text`; the history card shows the cleaned text by default and a *Show original* / *Show cleaned* button (`.upload-view-switch`) flips it. A passage the model failed on keeps its wording and the job notes it (`Text cleanup could not clean N of M passages ...`), the upload still saves. Every upload offers built-in TXT, SRT and VTT downloads (`transcription/exports.py`, registered through the export-target mechanism by `ExtensionRegistry.add_builtin_exports` before the extensions load); SRT/VTT cues come from the stored word timings (at most 2 lines of 42 characters and 7 s, a new cue at a pause of 1 s, a speaker change or a sentence end, `Speaker N:` on the first cue of each turn, the stored label of speaker 1 for meetings), and an upload without word timing answers the download with a message (500 `error`). **Delete:** every history card (uploads and meetings, in both lists) has a Delete button; it turns into an in-card "Delete this ...? This cannot be undone." with Delete / Cancel (`askDeleteFileTranscription`, never `confirm()`), then `DELETE /api/file-transcriptions/<id>` removes the row and the audio files (an upload's stored audio, a meeting's whole folder; a missing file does not block it; 404 for an unknown id, 500 with `error` when a file cannot be removed). **Rename:** every card name has a pencil (`.upload-rename`, `editFileTitle`): click opens a text field, Enter saves, Esc or blur cancels. `PATCH /api/file-transcriptions/<id>` with `{"title"}` sets `file_transcriptions.title` (trimmed, max 255, 400 beyond; empty clears it; 404 for an unknown id). `original_filename` never changes (it finds a meeting's folder and tells which folders have a transcript); the list payload carries `title`, the card and the export download name show it when set.

**Feedback (own tab, last entry of the sidebar, separate from the others)** - `<nav class="tabs tabs-footer">` holds the `#feedback-tab-button` (`data-tab="feedback"`), independent of the Settings tab; the button and `#tab-feedback` are `hidden` until `GET /api/settings` carries a `feedback_url` (built by `src/nexusvox/system/feedback_form.py` from `[support].feedback_form_url`, defaults to `https://nexusvox.app/feedback`; empty = no entry). The tab is a short form (`system/feedback_send.py`, `dashboard-feedback.js`): kind (`#feedback-kind`: bug, wish, other), message (`#feedback-message`, 3 to 5,000 characters) and *Include log* (`#feedback-include-log`, off by default). *Send* (`#send-feedback`) is the only thing that sends: `POST /api/feedback/send` makes the app post JSON (`kind`, `message`, `app_version`, `windows_version`, `hardware` and, with the box ticked, `log`) to `/api/app-feedback` on the host of `feedback_form_url`, with the `NexusVox/<version>` User-Agent and no Origin header; no file picker, no other request. *Show what will be sent* (`#feedback-preview-toggle`) asks `POST /api/feedback/preview` for the same report as text and refreshes while the inputs change. The log is the last 300 lines (at most 50,000 characters) of today's `nexusvox.log` since the app's last start, with everything `logsetup` fenced as dictated text replaced by `[dictated text removed]` (full-text logging on or off) and the Windows user name in paths replaced by `<user>`; a file without the start mark yields no log. Success clears the message; failure, a refusal (rate limit, daily cap, too large) and no connection each show their own red line and keep the text. *Open the web form* (`#open-feedback-form`, `window.open`) stays as the fallback, and the support address `nexusvox@nightshift-ai.de`. The app stays fully usable offline: nothing is requested until the click.

**Extension tabs** - an installed extension (`extensions.md`; contract in `docs/EXTENSIONS.md`) may add tabs and export links. On `DOMContentLoaded` `loadExtensions()` reads `GET /api/extensions`, appends a `.tab` button (`data-tab="ext-<id>"`) and an empty `.tab-content` section per panel (`bindTab` wires the click, `activateTab` calls `openExtensionPanel`), and keeps the export targets for the Upload history, where each upload gets a `.upload-export` download link per target; the hash restore waits for it. The panel's script is added on first open and draws through `NexusVoxExt.registerPanel(id, container => ...)`. With nothing installed the page shows no extra tab; the built-in TXT/SRT/VTT export links are always there, so a non-empty `exports` list does not mean an extension is installed. An upload action with an `available` check is greyed out with its reason as tooltip (`actions_unavailable` per row), and `text`/`cleaned_text` in the list pass through the extensions' `display_text` hook (the job `result` and the stored row stay raw). A state dict instead of a string (`{pending}` / `{error, retry}`) shows a spinner line or the reason with a Retry button under the card's links; while a list has a pending row, `loadFileTranscriptions(true)` polls only that list every 4 s (`createPendingPoller`; paused while the page is hidden or the list's tab is not shown, resumed on `visibilitychange`), the newest load wins (`loadGeneration`), and a poll replaces only the cards whose data changed. SRT/VTT are greyed out (`exports_unavailable`, tooltip `NO_TIMING_HINT`) for a row without stored word timing; TXT is the text as shown (cleaned when cleanup ran) while the subtitles use the words as transcribed. The panel blueprints are mounted by `_create_app` (a mount failure is logged, the dashboard stays up), and `upload_and_transcribe` adds `extensions` (per-extension results, `{}` when none) to the job `result`.

**Review**** — unreviewed recordings that have audio files, oldest first. Each card has *Retry* (`POST /api/review/<tid>/retry`): the stored WAV is transcribed again with the current model (same path as file upload, `transcribe_file`) and the result goes into the correction box; nothing is saved until the user submits. It needs the WAV, i.e. `[database].store_audio`, which the tab says. Users confirm correctness via checkbox or provide corrected text. Flagged-but-unreviewed items highlighted red with checkbox defaulting to incorrect. `reviewed` column on `Transcription` is tri-state: `0`=unreviewed, `1`=correct, `2`=incorrect.

**Dev (experimental: `[experimental].dev_tab`)**** — hidden and its `/api/benchmarks*` routes not registered unless the flag is on (`?dev` does nothing). Reads benchmark JSON files from `benchmarks/` directory. Two views: comparison mode (table + WER bar chart + RTF bar chart across all benchmarks) and detail mode (WER distribution histogram, latency scatter plot, sample explorer with word-level diff).
